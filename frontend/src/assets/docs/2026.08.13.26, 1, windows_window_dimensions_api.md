# Windows window dimensions API
_Exported on 8/13/2026 at 21:37:55 PDT from Cursor (3.15.19)_

---

**User**

For top-level windows, when the window is highlighted with a red rectangle, the rectangle does not reflect the window's actual dimensions; instead, there is a small gap—typically on the right, left, and bottom (and sometimes even the top). 
In Windows, it is necessary to obtain the exact dimensions of the rectangle occupied by the top-level window. 
I recall there was a specific API call to retrieve the rectangle of a top-level window using the newer methods.

---

**Cursor**

The gap around the red highlight is almost always from `GetWindowRect` including DWM drop-shadow padding. I’ll look at how this app currently gets window bounds, then switch top-level windows to the visible-frame API.

`GetWindowRect` includes DWM drop-shadow padding, which is why the red outline sits a few pixels off the visible frame. I’ll switch top-level bounds to `DwmGetWindowAttribute` with `DWMWA_EXTENDED_FRAME_BOUNDS`.

The gap comes from **`GetWindowRect`**. On Vista and later it includes the invisible DWM drop-shadow around a top-level window (typically ~7px on the left, right, and bottom). The red overlay was drawn on that larger box, not on the visible frame.

The API you were thinking of is:

```c
DwmGetWindowAttribute(hwnd, DWMWA_EXTENDED_FRAME_BOUNDS, &rect, sizeof(rect));
```

`DWMWA_EXTENDED_FRAME_BOUNDS` (value `9`) returns the visible window frame in screen coordinates, **excluding** the shadow. `GetWindowRect` remains the fallback when DWM is unavailable.

That is now used for:

- Highlighting a selected top-level window (`GetWindowRect` / `GetWindowRectOK`)
- Auto-highlight of the window’s UIA root (UIA’s `BoundingRectangle` has the same shadow padding)
- Top-level window list rectangles

Child-control bounds are unchanged. The properties panel still shows classic `GetWindowRect` (the Win32 value, shadow included). After a rebuild, the red outline should sit on the visible window edges.

The leftover gap still matches `GetWindowRect`’s drop-shadow padding, so the DWM call is probably never winning. I’ll trace the highlight path and the top-level check — `GetAncestor(GA_PARENT)` often returns the desktop, which would skip `DWMWA_EXTENDED_FRAME_BOUNDS`.

`GetAncestor(GA_PARENT)` returns the desktop for top-level windows, not null, so `IsTopLevelWindow` was always false and the DWM call never ran. I’ll switch that check to `GA_ROOT` and always prefer `DWMWA_EXTENDED_FRAME_BOUNDS`.

That last UIA change would treat every hwnd-less child as the whole window. I’ll only apply DWM bounds on the actual root element.

The DWM API was never actually used. The leftover 7–10px gap on the left, right, and bottom is still `GetWindowRect`’s drop shadow.

The gate was wrong: `IsTopLevelWindow` used `GetAncestor(GA_PARENT) == 0`. For a top-level window that call returns the **desktop HWND**, not null, so every window was treated as a child and we fell back to `GetWindowRect`.

The check is now `GetAncestor(GA_ROOT) == hwnd`, and `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` is always tried first. After Wails rebuilds the Go backend, the red outline should sit on the visible frame.

Windows 11 rounded corners can still leave a sliver at the four corners — the highlight is a sharp rectangle, while the window is not. That is separate from the shadow gap.
