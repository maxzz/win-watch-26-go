I'll compare how each app saves and restores window position—traytools stays put across monitors, so the difference is likely in restore coordinates or how Wails applies them.

Wails treats `WindowSetPosition` as an offset from the current monitor, while we persist absolute virtual-screen coordinates—that mismatch is why the window lands on the third display. I'll port traytools' absolute-position restore.

The jump came from a Wails Windows quirk that traytools already works around. We saved **absolute** virtual-screen coordinates (`WindowGetPosition` → `GetWindowRect`), then restored them with `WindowSetPosition`, which treats `(x, y)` as an **offset from the current monitor’s work-area origin**. Windows often creates the new window on a different display (cursor, last-used monitor, etc.), so those saved numbers were applied relative to the wrong screen — commonly the third monitor.

Traytools cancels that offset by probing the origin first:

1. `WindowSetPosition(0, 0)`
2. Read the resulting absolute position (the monitor origin)
3. `WindowSetPosition(savedX - originX, savedY - originY)`

That helper is now in `backend/winapp/window_position_windows.go`, and startup restore uses `winapp.SetWindowPositionAbsolute` instead of a raw `WindowSetPosition`. Rebuild and the window should reopen on the same monitor it closed on.
